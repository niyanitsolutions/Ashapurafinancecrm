Dependency order for implementation: Foundation → Auth → User & Employee Management → Access Control → Settings (Master Data) → Dashboard Framework → Lead Management (6A → 6B → 6C → 6D) → ..., per `docs/roadmap/TODO.md`. Settings (Master Data) is the first module built after Access Control and gates every one of its endpoints (not just writes) with `require_permission(...)` — see decision 026. Dashboard Framework's widgets/nav items follow the same pattern and are additionally designed to be forward-compatible with modules that don't exist yet (decision 032) — proven out by 6A, which wired two of Dashboard's own placeholder widgets to real data (decision 044) without touching Dashboard's engine. 6B is the first module to knowingly deviate from `require_permission` for a whole sub-area (staff visibility, decision 050) — a considered choice, not an oversight, since the brief itself doesn't call for delegable access there. 6C is the first module to give real substance to the `workflow_engine`/`event_engine` folders (reserved since Foundation, decision 005) and reverses 6B's own decision 050 back to real `require_permission` gating (decision 059), since Loan/Insurance processing genuinely is a delegable, multi-step business process unlike 6B's inherent assignment-scoped visibility. 6D reuses 6C's own "poll `audit_logs` instead of a live hook into a frozen module" pattern (decision 058 → 065) to react to Lead assignment and document uploads, and is the first module to actually schedule Arq jobs (`app/worker/tasks/`, reserved since Foundation, decision 002).

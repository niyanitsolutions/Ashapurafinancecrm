# Known Limitations

- **No multi-tenancy.** `tenant_id` was deliberately deferred to Phase 2 (decision 001). Every collection built before multi-tenancy is added will need a migration + repository-layer query update at that point. This is a conscious tradeoff, not an oversight.
- **Integration clients are stubs.** `backend/app/services/{meta,whatsapp,sms,email,maps}` define the call interface but raise `NotImplementedError` — real provider wiring happens when System Settings/Integrations is built and the owner supplies credentials.
- ~~**`geo_fencing` has no defined use case yet.**~~ Resolved by Module 10 (Stage 1 of the Geo Fencing / Temporary Permissions / MSG91 request) — see that module's own section below.
- **Encryption key reuses the JWT secret — now actively used, not just a future concern.** `backend/app/security/encryption.py` derives its Fernet key from `JWT_SECRET_KEY` as a placeholder. Module 2 started actually encrypting a real sensitive field with it (Employee bank account numbers, decision 018) without resolving this — a dedicated `ENCRYPTION_KEY` setting should be introduced before production so JWT signing and field encryption don't share key material. Higher priority now than when this was first written.
- **Backup/restore scripts are manual stubs.** `scripts/backup.py` / `restore.py` wrap `mongodump`/`mongorestore` for local use only — no retention policy, no automated schedule, no offsite storage. Must be replaced with a real strategy (possibly AWS/GCP managed backups) before production.
- **CI's `pytest --maxfail=1 -q || [ $? -eq 5 ]` no-tests-yet escape hatch is now moot but left in place.** `tests/api/test_auth.py` (15 tests) means exit code 5 won't happen anymore for a healthy build, but harmless to leave for future modules that might temporarily have zero tests in `tests/{unit,integration,e2e,performance}`.
- **`react-router-dom` pinned to `7.18.1`, not the latest audit-clean version.** `npm audit` flags GHSA-qwww-vcr4-c8h2 (RSC-mode CSRF bypass) affecting `>=7.12.0 <8.3.0`; the only fixes are downgrading to v6 or upgrading to v8, both breaking changes disproportionate to this scaffold's `createBrowserRouter`/`RouterProvider`-only usage (no RSC, no server actions — the vulnerable code path isn't reachable). Revisit if/when routing usage grows to use data-mode loaders/actions.
- **`eslint`'s transitive `brace-expansion` has a known DoS advisory** (dev-tooling only, not shipped in the production bundle). The fix requires an eslint 9→10 major bump; deferred as a deliberate upgrade to evaluate separately, not bundled into this scaffold.
- **Frontend production bundle has crossed Vite's 500kB warning threshold** (~535kB as of Module 6B, up from ~506kB after Module 6A). Still one bundle, no code-splitting — reasonable for the app's current size, but worth revisiting (route-level `import()` splitting) once more feature modules (Loan/Insurance/Referral pipelines) land and the bundle keeps growing.

## Module 1 — Authentication

- **Secure-link tie-in to a specific Lead/application is not built.** Decision 003's "scoped to one resource" half needs Lead Management to exist (there's no resource to scope to yet). Signup is now invitation-only and role-authorized (decision 011), but the invitation is still delivered as an OTP to a phone number, not a clickable link opening a specific application. `backend/app/security/tokens.py`'s `issue_secure_link_token`/`decode_secure_link_token` remain unused until Lead Management wires them in.
- **No invitation-triggering UI.** `POST /auth/send-otp` requires an authenticated Owner/Employee and is fully tested via API, but there's no frontend screen with an "invite this customer" button — that belongs to a future Owner/Employee portal, out of scope this module. Right now the only way to trigger an invitation is a direct API call.
- **`dev_otp` is echoed in the API response outside `production`.** `send-otp`/`forgot-password` return the raw OTP directly in non-prod environments (`backend/app/features/auth/service.py:_dev_otp_echo_enabled`) since no real SMS provider is configured (see the integration-stubs limitation above). This must never be relied upon once `services/sms` is wired to a real provider — check `app_env` behavior explicitly before any production deploy, don't just trust the flag.
- **GeoIP is an unconfigured stub** (`backend/app/services/geoip/client.py`, same pattern as SMS/WhatsApp/email) — `Session.city`/`Session.country` are always `null` until a real provider is wired in via System Settings/Integrations.
- **Refresh token is persisted to `localStorage` on the frontend**, not an HttpOnly cookie (pure Bearer was chosen, decision 008) and not held only in memory (would force re-login on every page reload, with no Dashboard/shell yet to make that tolerable). This was reviewed explicitly as decision 012: it's the standard, examined tradeoff of cookie-less SPA auth — any browser storage is JS-readable (XSS exposure) — mitigated by (a) the access token staying memory-only and (b) refresh token rotation with family-wide reuse detection (decision 013), which bounds a stolen token to at most one use before the whole session family is killed.
- **`change-password` has no frontend UI.** The API exists and is tested; the page would naturally live in a Settings/Profile screen, which is out of scope for this module.
- **No Session Management screen.** The `sessions` collection, rotation-chain, and revocation mechanics exist (decisions 009, 013) but nothing displays or lets a user revoke another session yet.
- **`login_method` only ever has one value (`"password"`).** The field exists (decision 014) for when OTP-based or invitation-triggered login is added; there's no dead branching for those yet, just the one real value in use today.
- **Encryption key placeholder is still unresolved** (see the entry above) — Authentication doesn't itself need field encryption yet (no bank account numbers/PAN stored), so this wasn't forced to a resolution this module either.
- **No automated browser testing.** Frontend verification for this module was `tsc`, `eslint`, `vite build`, and a dev-server serve/compile smoke test only — no actual browser exercised the login/invite/OTP/reset click-through flows, since no browser automation tool was available in this environment.

## Module 2 — User & Employee Management

- **`on_leave` not blocking login is a guess, not a confirmed business rule.** Flagged explicitly in decision 016 — every other employment status (inactive/suspended/resigned) blocks login, but whether an on-leave employee should retain portal access wasn't specified in the brief. Worth explicit confirmation before relying on it.
- **No delete action.** `BaseRepository.soft_delete` is available on `EmployeeRepository` (inherited) but no router endpoint calls it — the Owner Features list has Deactivate but not Delete, so none was built. If a real delete requirement shows up later, the plumbing is already there.
- **Employee documents (PAN/Aadhaar/offer letter/etc.) have a working API but no frontend page.** Neither the Owner Features list nor the Employee Portal list explicitly named a document-upload action, but the data model (`employee_documents` collection) and "Documents" field group in the brief clearly anticipated one — built the backend (presigned-upload-then-confirm, same pattern as the photo flow) so the collection isn't dead, but didn't invent a UI page not listed in this module's frontend scope.
- **Master data (departments/designations/branches) has no management UI.** Owner-only list/create API endpoints exist and are seeded with starter data, but per the user's own roadmap change, full CRUD screens are deliberately deferred to a future Settings (Master Data) module (decision 019) rather than built ad hoc here.
- **Mobile number is denormalized onto `Employee.mobile` at creation time.** Convenient for search/list without a join back to `users`, but there is no "change mobile number" flow anywhere in the system yet (Auth doesn't have one either) — if one is ever built, it must update both `users.mobile` and every `Employee.mobile` copy, or this will silently drift.
- **No automated browser testing**, same caveat as Module 1 — verification was `tsc`/`eslint`/`vite build`/dev-server smoke test only, no real browser exercised the Employee List/Create/Edit/Profile click-through flows.
- **CSV export button likely never actually worked.** *(Discovered while building Module 6A — not something Module 2 broke, a pre-existing gap noticed only now.)* `EmployeeListPage`'s "Export CSV" is a plain `<a href={exportEmployeesCsvUrl()}>` — since this app is pure-Bearer with no cookies (decision 008), a plain anchor navigation can't carry the `Authorization` header, so the request would 401 rather than download. Module 6A's own Lead export uses a real authenticated `fetch`-to-blob download instead (`shared/api/client.ts:getAccessToken`) and doesn't repeat this pattern, but Module 2's own button was left as-is rather than editing a frozen file for an unrequested fix — worth a real bug-fix pass under the freeze policy's security/bug-fix exception (decision 031).

## Module 3 — Role, Permission & Access Control

- **Daily recurring time window is an interpretation, not a confirmed spec.** The brief gave four separate fields (Start Date, End Date, Start Time, End Time) for Temporary Access and Geo Exceptions; decision 022 chose to read this as a *daily recurring* window (date range × a "HH:MM"–"HH:MM" band repeated every day in that range) rather than one continuous start-to-end span. Worth explicit confirmation before relying on it for a real access grant.
- **Overnight windows aren't supported.** The `start_time < end_time` string comparison in `PermissionEngine._within_daily_window` can't express a window like `22:00`–`06:00` that crosses midnight — such a grant would simply never be satisfied. Not flagged as a validation error at creation time; a role/access record like this would silently never grant access.
- ~~**Geo Exception has no enforcement engine to except from.**~~ Resolved by Module 10 — `GeoException` is now checked by `app/features/geo_fencing/enforcement.py` for the two activities that have real enforcement wired up (Lead Creation, Document Collection). Decision 123 later removed the `geo_fence_id`/coordinate fields decision 110 had added: a `GeoException` carries no location of its own — it's a bypass of the employee's applicable Geo Fence(s), not a second one.
- ~~**`PermissionEngine`/`require_permission` is unused by any real endpoint.**~~ Resolved by Module 4 — every Settings (Master Data) endpoint is gated with `require_permission("system_settings", ...)` (decision 026). Module 2 remains deliberately not retrofitted (decision 024).
- **`AssignRolePage` requires knowing the employee's raw ID.** There's no employee search-by-name/autocomplete on that page yet — the Owner has to already know or look up the `employee_id` (e.g. from the Employee List page) before assigning a role. A future pass could add a proper picker.
- **No delete action**, same pattern as Module 2 — roles/permissions/grants support deactivate/revoke (and permissions are soft-deletable via inherited `BaseRepository.soft_delete`) but no hard-delete endpoint is exposed.
- **No automated browser testing**, same caveat as Modules 1 and 2 — verification was `tsc`/`eslint`/`vite build`/dev-server smoke test only, no real browser exercised the Role/Matrix/Assign/Temporary-Access/Geo-Exception click-through flows.

## Module 4 — Settings (Master Data)

- **Status Masters and Notification Templates ship with zero example rows, by design.** The brief named categories/channels but no concrete status values or message copy — decision 029 deliberately left these empty rather than inventing business content. The screens work; there's just nothing in them until the Owner adds real values.
- **Notification Templates have no consumer yet.** The collection/CRUD exists, but nothing renders a template against real data — that's the future Reminder & Notification Engine module's job. `available_variables` is purely documentation for whoever builds that module, not enforced anywhere.
- **API Settings config is genuinely write-only.** Once a key is set, there's no way — via the API or UI — to see its value again, only that it's configured (`configured_keys`). This is intentional (decision 028), but means a mistyped secret must be *overwritten*, not corrected in place; there's no "reveal" or diff view.
- **No "test connection" action for API Settings.** The brief listed API Settings as a master-data category, not a live-integration-testing feature — `app/services/{meta,whatsapp,sms,email,maps}` remain the same unwired `NotImplementedError` stubs noted in the general limitations above regardless of what's configured here.
- **Company Settings' color/logo fields are stored but not applied at runtime.** The frontend still renders the fixed Tailwind theme tokens from `docs/REQUIREMENTS.md`'s Dashboard Theme section — wiring `primary_color`/`secondary_color`/`logo_s3_key` into the actual UI (dynamic theming) is out of scope for a master-data CRUD module. Dashboard Framework (Module 5) built the real `AppShell`/Sidebar/Topbar this would apply to, but deliberately didn't wire dynamic theming either (kept to the fixed token set) — still open for a future pass.
- **Business Hours aren't enforced anywhere.** They're stored on Company Settings but nothing currently reads them (no attendance/access-window logic consumes them) — purely a data-entry screen today.
- **Branch address editing has no frontend UI.** The `PATCH /branches/{id}` API accepts an `address` field, but `BranchesPage` only exposes name/code/phone — the same "backend supports it, no page surfaces it yet" pattern as Module 2's employee documents.
- **No delete action anywhere in this module**, same pattern as every prior module — deactivate covers the "remove from active use" need; nothing is hard-deleted.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/dev-server smoke test only. No live MongoDB/Redis was available in this environment either (no Docker), so the equivalent of a dev-server smoke test against real infrastructure wasn't possible this round — verification relied on the backend's mongomock/fakeredis test suite (65/65 passing) plus static frontend checks.

## Module 6A — Lead Foundation

- **Duplicate matching is mobile-only, not time-windowed, and not scoped by product.** A person with an old, unrelated Loan lead from a year ago will flag a brand-new Insurance lead as a "possible duplicate" — matching on `mobile` alone was a deliberate simplification (decision 041), not a considered product rule. Worth confirming whether product-category scoping or a time window is actually wanted before relying on the flag operationally.
- **No row-level "only see my assigned leads" restriction.** Any Employee granted `leads:leads:view` can see every Lead company-wide, not just ones assigned to them — a common-enough CRM pattern (full sales-team visibility) but not something the brief explicitly confirmed. `RolePermission`'s existing `department_ids`/`branch_ids` scoping (Module 3) isn't applied here since `Lead` has no department/branch field.
- **Creating/editing a Lead needs two separate permission grants to fully work for a non-Owner.** `leads:leads` gates the Lead itself, but the Create/Edit form's Source/Product dropdowns call Module 4's own `system_settings:lead_sources`/`loan_products`/`insurance_products` endpoints, each gated by its own permission (decision 045). An Owner granting only `leads:leads` to a role will find that role's Create Lead form has no dropdown options.
- **`AssignLead` on the Lead Details page needs the raw Employee ID**, same pattern as Module 3's `AssignRolePage` — no employee search/autocomplete. The Owner has to look up the ID from the Employees list first.
- **No real Website/Meta lead-capture webhook.** `source_id` only records where a lead is *said* to have come from — there's no actual inbound integration receiving leads automatically from those channels yet (decision 043); that's future Integrations-module work.
- **Timeline pagination doesn't exist.** `GET /leads/{id}/timeline` returns up to 500 combined activity+note entries with no paging — fine for a Lead's realistic activity volume today, would need real pagination if that assumption stops holding.
- **No delete action**, same pattern as every prior module.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks only; no live MongoDB/Redis was available in this environment (no Docker), so verification relied on the backend's mongomock/fakeredis test suite (88/88 passing) plus static frontend checks.

One residual trace remains: the `OTP_SENT` audit-log entry still names the technical Owner as `user_id`, because `audit_logs` is intentionally append-only (`shared/audit_log.py`, no update/delete path) — accepted as a minor, non-attributable log artifact, not a data-model issue.

The user has explicitly instructed that these specific seeded rows (not the form engine itself) will be replaced later with Ashapura-approved Personal/Business/Home Loan and Health/Life Insurance field definitions, via a data-only change (decision 051's clarification). Do not treat the current fields as confirmed business requirements.
- **No Owner-facing form-builder UI.** Form definitions can only be seeded (`scripts/seed.py`), never created/edited via the API — the brief's own Owner-capability list for 6B doesn't include form authoring, so none was built. A future module would need to add this deliberately, not as an oversight.

- **Employee's assignment-scoped visibility has no department/branch nuance.** Same limitation shape as Module 6A's Leads — an Employee sees exactly what's assigned to them, nothing scoped by department/branch on top of that (there's no delegation model here at all per decision 050, so this is even more hard-coded than 6A's).
- **No document preview/thumbnail**, just a filename + download link (presigned S3 URL, `generate_presigned_download_url`) — consistent with every other document-handling screen in this project (Module 2's employee documents included).
- **`pending_profile`'s fields are a fixed, small set** (full name + email in the current `ApplicationPage.tsx`) — not the complete `CompleteProfileRequest` shape (date of birth, PAN, Aadhaar, address are omitted from the inline Flow-1 UI, though the backend schema and `submit_application` accept all of them). A more complete inline profile form is a frontend-only follow-up, not a backend limitation.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks only; no live MongoDB/Redis was available in this environment (no Docker), so verification relied on the backend's mongomock/fakeredis test suite (94/94 passing) plus static frontend checks. The dual-flow onboarding UX in particular (secure-link landing → login/OTP detour → resume) was verified by code review and backend integration tests only, never an actual browser click-through.

## Module 6C — Loan & Insurance Processing Pipeline

- **Insurance lifecycle — resolved.** The draft flagged as an assumption (decision 057) was reviewed and replaced by the user with a finalized sequence (decision 064): Application Submitted → Documents Pending → Underwriting → Medical Verification (optional) → Additional Documents (optional) → Premium Acceptance → Policy Generation → Policy Issued. No longer a placeholder.
- **Case creation is lazy (get-or-create on first read), not truly instantaneous.** A Loan/Insurance Case exists no later than the first time any Owner/Employee/Customer looks at the relevant list or detail endpoint after the Application is submitted — in practice indistinguishable from real-time for a human user, but there is no live push the instant `Application.status` becomes `submitted` (decision 058). This was a deliberate trade-off: hooking into Module 6B's frozen `submit_application` isn't permitted, and a MongoDB change-stream watcher (the alternative that *would* be instant) isn't exercisable by this project's mongomock-based test suite (no live MongoDB in this environment).
- **No Customer-facing frontend was built** (decision 062, per the brief's own "Do NOT build Customer Portal enhancements" instruction). `GET /loan-cases/mine`, `POST /loan-cases/{id}/offer/accept`/`decline`, and the Insurance equivalents all exist and are tested, but a Customer currently has no screen to view case status or accept/decline an offer/premium — only reachable via direct API call. Flagged as a future, explicitly-requested Customer Portal enhancement, not an oversight.
- **Credit evaluation, eSign/NACH/KYC, and medical examination are all staff-recorded manual steps.** No live credit bureau, e-sign provider, NACH mandate registration, or diagnostic-lab integration exists anywhere in this project — consistent with how every other unbuilt external integration has been handled (the `app/services/{whatsapp,sms,email,maps}` stubs remain unwired regardless).
- **`event_engine.publish()`/`WorkflowDefinition.notification_trigger_key`/`reminder_trigger_key` remain inert placeholders even after Module 6D.** Module 6D's own notifications for Loan/Insurance Cases (the Re-Eligible reminder) were built by polling `application_workflows`/`application_status_history` directly (decision 065), not by subscribing to `event_engine`'s `workflow.status_changed` event — so 6C's own publish-after-every-transition call still has zero subscribers, and `notification_trigger_key` is still never read by anything. A future round could register a 6D subscriber on that event instead of (or alongside) the polling approach, but this hasn't been done. No SMS/WhatsApp/email is sent for any Loan/Insurance Case event — that remains `notification_management`'s job, still unbuilt.
- **No rollback in v1** (decision 056) — a case that reaches `rejected` cannot be moved backward through the API; correcting a wrong rejection currently requires direct database intervention, not a supported action. This is distinct from **"On Hold"/"Resume"** (decision 064), which pauses a non-terminal case and later resumes it back to the *exact same* status it paused at — not a move to an earlier stage, and not usable on a already-`rejected`/terminal case.
- **The document-type picker on both Case Details pages depends on a separate Settings permission.** `documentTypesApi.list()` (`GET /document-types`) is gated by `require_permission("system_settings", "document_types", "view")` — an Employee granted only `loan_management`/`insurance_management:applications` actions won't see any document types to request unless *also* granted that Settings permission. Same cross-module permission dependency shape as decision 045 (6A's Lead form dropdowns).
- **No historical record of exactly which document types were requested when, once fulfilled.** `pending_document_type_ids` is cleared on verification; the fact a request happened is only visible via the generic `workflow_documents_requested` audit-log entry, not a dedicated, queryable request history.
- **Bank/NBFC details are never enforced as required** before a Loan Case leaves Documents Pending — they can be left blank all the way to Disbursed. Recording them was scoped as a data-capture capability (decision 061), not a gated requirement; if the business wants them mandatory before Credit Evaluation, that's an explicit follow-up validation rule, not implemented here.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks plus the backend's mongomock/fakeredis test suite (103/103 passing); no live MongoDB/Redis was available in this environment.

## Module 6D — Reminder & Notification Engine

- **No live push — all three scheduler jobs run on a fixed polling interval.** `poll_audit_events` every 5 minutes, `check_task_reminders` every 15 minutes, `check_re_eligible_cases` once daily. A notification can lag the real underlying event by up to that interval — e.g. a Lead assigned at 9:00 might not generate a notification until 9:05. This is an inherent trade-off of a polling-based scheduler (no live event hook into frozen modules is possible — decision 065), not a bug.
- **`document_uploaded` notifications require the Application to already be assigned at poll time.** If a Customer uploads documents before an Owner assigns their Application to an Employee, that specific upload is silently skipped — there's no retroactive "catch-up" notification once the Application is later assigned. Only future uploads (after assignment) generate a notification.
- **`event_engine`'s `workflow.status_changed` publish (Module 6C) still has zero subscribers.** 6D's own Loan/Insurance-Case notifications were built by directly polling `application_workflows`/`application_status_history` (decision 065), not by subscribing to that event — so `WorkflowDefinition.notification_trigger_key`/`reminder_trigger_key` remain unread by anything, exactly as before 6D. See the Module 6C entry above.
- **`check_task_reminders` assumes exactly one active `task_due` rule.** The service supports creating multiple, but the scheduler job only reads `active_rules[0]` — if an Owner creates a second active `task_due` rule, the newer/other one is silently ignored by the job (though still visible/editable via the API). A future refinement would need the job to either merge or explicitly choose among multiple active rules of the same type.
- **No Owner oversight view of other users' notifications.** Each user (Owner included) sees only their own inbox — there's no "view all notifications sent" screen for auditing purposes; the `audit_logs` collection (`notification_created` events) is the only cross-user trail.
- **The Notification Bell's own rendering wasn't customized.** `NotificationBell.tsx` (Module 5, frozen) still `JSON.stringify`s each item rather than rendering a formatted title/message — the underlying data is now real (decision 070), but that dropdown's presentation wasn't touched, since editing it would mean modifying a frozen Dashboard file beyond the already-precedented `widget_providers.py` extension point. The dedicated `NotificationListPage` (`/notifications`) renders properly; the Bell dropdown is a secondary, lower-fidelity surface.
- **Task editing (`PATCH /tasks/{id}`) has no frontend form.** The API exists and is tested; `TaskListPage` only exposes create (Owner) and complete (assignee) — editing an existing task's title/description/due date is reachable only via direct API call.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks plus the backend's mongomock/fakeredis test suite (112/112 passing); no live MongoDB/Redis was available in this environment, and the Arq worker itself was never run live (its cron jobs were unit-tested by calling the job functions directly, not via a running `arq` process).

That belongs to Reports & Analytics"), the self-service dashboard is deliberately minimal (totals + recent leads only) — no charts, exports, or historical trend views. That's Reports & Analytics' job, not yet built.
- **`check_commission_triggers` re-scans every case currently in a terminal "success" status on each daily run**, rather than tracking a checkpoint of newly-terminal cases — safe (idempotent via a unique index on `commission_entries.case_id`) but not maximally efficient at large scale, the same trade-off `check_re_eligible_cases` (Module 6D) already makes for its own daily rejected-case scan.
- **Only one Commission Rule ever applies per (product, partner, trigger) combination** — if the Owner creates two active rules that would both match, `_pick_rule`'s "most specific wins" ordering (partner+product > partner+all > default+product > default+all) picks exactly one deterministically; there's no "combine multiple rules" or warning if two same-specificity rules conflict (whichever is returned first from the query wins in that tie case).
- **No Owner-facing view of a Referral Partner's full lead-to-application-to-case chain in one place** — the Owner sees the Referral Partner list, the Commission Ledger, and Leads/Loan/Insurance Cases separately; there's no combined "trace this referral end-to-end" screen. Reachable by cross-referencing `referral_leads`/`applications`/`application_workflows` manually.
- **A Referral Partner cannot see who their assigned Employee is**, nor any staff-side notes/timeline — by design (decision 078's "never expose internal status" extends to internal staff assignment, not just status).
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks plus the backend's mongomock/fakeredis test suite (117/117 passing); no live MongoDB/Redis was available in this environment.

## Module 8 — Reports & Analytics

- **Scheduled Reports are framework only — nothing ever runs one.** Full CRUD exists (`/scheduled-reports`), but no Arq job reads `is_active`/`frequency` to actually execute and distribute a report; `last_run_at` is never set by any code. Per explicit instruction ("Scheduled Reports (framework only)") — a future round would add the actual distribution job on top of this same schema, not a new one.
- **"Loan Approved" uses `loan_details.offer_decision == "accepted"`** as the closest concrete stand-in for "approved" — `ApplicationWorkflow` (decision 055's schema) has no separate credit-approval boolean/timestamp distinct from the customer's own offer acceptance.
- **"Loan Rejected"/"Insurance Rejections" use `updated_at`** as the report's date field — neither case type stores a dedicated `rejected_at` timestamp, so the most recent update (in practice, almost always the rejection itself) is used as a proxy. A future schema addition to 6C could add a real `rejected_at` field if this proves inaccurate in practice.
- **"Leads by Product" resolves a product name checking `loan_products` then `insurance_products`, keyed only by `product_id`** — collision between the two collections' ObjectIds is astronomically unlikely (not the same document, just theoretically possible matching hex values) but not structurally prevented, since the report doesn't carry a compound (category, id) lookup key end-to-end.
- **No cross-report drill-down.** Clicking a row (e.g. a Bank in "Bank Performance") doesn't navigate to that bank's underlying case list — each report is a standalone table, not a linked drill-down hierarchy.
- **No chart/graph visualizations.** Every report renders as a table (plus a small summary strip for reports that have one) — no bar/line/pie chart rendering was built, consistent with the brief's own report list (which named report *content*, not a charting requirement).
- **`check_commission_triggers`-style incremental scanning wasn't applied to reports** — every report recomputes its full aggregation on every call (no caching, no materialized view). Fine at this project's expected data volume; would need revisiting if lead/case counts grow into the hundreds of thousands.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks plus the backend's mongomock/fakeredis test suite (127/127 passing); no live MongoDB/Redis was available in this environment.

## Module 9A — API Management

- **Encryption key is still the Foundation-era placeholder.** `app.security.encryption` derives its Fernet key from `JWT_SECRET_KEY` (padded/truncated to 32 bytes) rather than a dedicated `ENCRYPTION_KEY` setting — a known limitation since decisions 018/028, unchanged by this module. Rotating the JWT secret would also invalidate every encrypted integration config.
- **WhatsApp/SMS/API-based Email Test Connection is a reachability check, not a full provider-specific validation.** Since the brief itself asks these to support arbitrary future providers, there's no single fixed API contract to authenticate against more deeply — the test confirms the stored URL is reachable and (if a token is set) sends it as a Bearer header, but can't verify the credential is actually *valid* the way the Meta/Google Maps/SMTP checks can. A future 9B/9C round, once a specific provider's real SDK is wired in, could tighten this per-provider.
- **No secret "reveal."** Once a secret field is set, there is no way — via the API or UI — to see its value again, only that a masked form exists; a mistyped secret must be overwritten, not corrected in place. Same posture as `system_settings.ApiSetting` (decision 028) and Employee bank account masking (decision 018).
- **No delete endpoint for `IntegrationConfig`.** Matching Reminder Rules'/Commission Rules' own precedent (no hard-delete, only activate/deactivate), a config can only be disabled, not removed — the brief's own frontend scope didn't list a Delete screen either.
- **`IntegrationConfig.health_status` is inert by design.** Reserved per explicit instruction ("no need to implement now, just reserve it for later") for a future Healthy/Warning/Error operational view — no code computes or reads it yet (decision 096). Not a gap; a deliberately empty slot, same pattern as `ReferralPartner.parent_partner_id`.
- ~~**No webhook verification/receipt handling yet.**~~ Resolved by Module 9B — `webhook_verify_token`/`webhook_secret` are now read and validated by the real Meta webhook handshake/signature check.
- **`system_settings.api_settings` and `integration_configs` now have overlapping purpose** (both can store Meta/WhatsApp/SMS/Email/Maps credentials) — nothing migrates existing `ApiSetting` rows into the new collection, since `system_settings` is frozen and out of scope to modify. Worth a future explicit cleanup decision if `ApiSetting` still holds any of these five providers' real credentials.
- **`docs/REQUIREMENTS.md` has no dedicated sections for Module 7 (Referral Partner Portal) or Module 8 (Reports & Analytics)** — an earlier-round documentation gap noticed while updating this file for 9A, not introduced by this module. Not backfilled now to stay in scope; flagged here as a follow-up.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks plus the backend's mongomock/fakeredis test suite (134/134 passing); no live MongoDB/Redis was available in this environment, and no real Meta/WhatsApp/SMS/SMTP/Google Maps credentials exist anywhere in this project — every Test Connection code path is exercised in tests via monkeypatching, never a live external call.

## Module 9B — Lead Capture

- **Meta's own lead field names vary per form** (an Owner names their own form fields in Meta's UI) — `meta_client.parse_field_data`'s mapping only recognizes a fixed set of common names (`full_name`/`name`, `phone_number`/`phone`, `email`). A Meta form using different field names for these would produce a `missing_required_fields` capture failure even though the data technically exists under an unrecognized key. A future round could make this mapping configurable per form.
- **Meta Lead Ads has no per-form product mapping** — only one Loan/Insurance product default per Meta channel as a whole (`CaptureSource.default_product_category`/`default_product_id`), not one per Meta form/campaign. An Owner running multiple Meta lead forms for different products would need to route them through separate manual reclassification, since there's no `form_id → product` table yet.
- **Website form capture has no idempotency check** (unlike Meta's `CaptureReceipt`) — a double-submitted web form (e.g. a visitor clicking "Submit" twice) creates two Leads, relying entirely on Module 6A's own cross-lead `duplicate_of_lead_ids` flagging to surface it to staff, not preventing it outright.
- **No bulk/CSV import** — "Manual API" is a single-lead controlled-capture endpoint, not a bulk importer. The brief itself framed this as aspirational ("Future POST /api/v1/leads/import or similar"); a batch-import feature would be a separate, larger addition.
- **`Lead.created_by=None` for system-actor captures means the Owner used internally is otherwise invisible** — only visible via `write_audit_log`'s own `user_id` field in `audit_logs`, not on the Lead itself. This is intentional (decision 098), not an oversight, but worth knowing when auditing.
- **No live webhook test was possible** — there are no real Meta credentials, no real Meta app, and no publicly reachable URL for Meta to actually call in this environment. The webhook verification handshake, signature check, and Graph API retrieval are all real, working code, but only exercised in the test suite via monkeypatching (`tests/api/test_lead_capture.py`), never against Meta's actual servers.
- **`webhook_events` is inert by design.** Reserved per explicit instruction ("no need to implement now — just keep it in mind for future observability") for a future record of every inbound webhook event, not just failures — no code reads or writes it yet (decision 103). Not a gap; a deliberately empty slot, same pattern as `IntegrationConfig.health_status`.
- **Lead Source Metadata / Website Form Version is a best-effort passthrough, not a guarantee.** `extract_source_metadata` only captures `form_id`/`form_version`/`campaign_id`/`adset_id`/`ad_id`/`utm_source`/`utm_campaign`/`utm_medium` when a source's own raw payload happens to include them — a Website form that doesn't pass UTM params, or a Meta webhook payload that doesn't carry ad/campaign identifiers, simply has an empty `source_metadata` dict on that Lead's Timeline entry. No ROI/Campaign reporting was built on top of this data yet (decision 103) — that would be a future Reports & Analytics addition.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks plus the backend's mongomock/fakeredis test suite (144/144 passing); no live MongoDB/Redis was available in this environment.

## Module 9C — Communication Engine

- **WhatsApp/SMS adapters are a generic HTTP POST, not a specific provider's real SDK/API contract.** Same "the brief itself asks for arbitrary future providers, so there's no one contract to target" limitation 9A's own Test Connection already disclosed (decision 105) — a future round wiring in a specific provider's real SDK could tighten the request/response shape per provider.
- **No delivery-status webhook exists for any channel** — `QueueStatus.DELIVERED`/`CommunicationQueueItem.delivered_at`/`CommunicationHistory.delivered_at` are reserved fields only; every message that sends successfully stops at `sent`, never advances to `delivered`. Adding real delivery-status tracking (WhatsApp/SMS delivery receipts, email open/bounce webhooks) is future scope.
- **Recipient resolution is best-effort against denormalized contact fields.** If an Employee/Customer/Referral Partner record is missing a mobile or email (or was deleted after the triggering audit-log row was written), the poller silently skips that channel or that event entirely — there is no `capture_failures`-style record of a business event that couldn't be resolved to a recipient, unlike Module 9B's own capture pipeline. A future round could add an equivalent "unresolvable event" log if this proves to matter in practice.
- **OTP is deliberately never routed through this engine.** `TemplateCategory.OTP` exists only as a reserved vocabulary value — Auth (Module 1) is frozen and OTP delivery must remain synchronous; a queued, polled send would defeat the purpose of an OTP. Not a gap, an explicit architectural exclusion (decision 106).
- **`communication_preferences` is inert by design.** Reserved per explicit instruction ("prepare for future support... do not implement UI yet") — no code reads it before enqueueing or sending. Not a gap; a deliberately empty slot, same pattern as `IntegrationConfig.health_status` (decision 096) and `webhook_events` (decision 103).
- **No live provider send was possible** — there are no real WhatsApp Business API, SMS gateway, or SMTP credentials anywhere in this project. Every adapter is real, working code, but only exercised in the test suite via monkeypatching `app.features.communication.adapters.ADAPTERS` (`tests/api/test_communication.py`), never against a live provider.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks plus the backend's mongomock/fakeredis test suite (151/151 passing); no live MongoDB/Redis was available in this environment.

## Module 10 — Geo Fencing (Stage 1 of the Geo Fencing / Temporary Permissions / MSG91 request)

- **Only 2 of the 5 `allowed_activities` values are actually enforced.** `lead_creation` (`POST /leads`) and `document_collection` (`POST /{case_id}/documents/verify` on both Loan and Insurance cases) call `enforce_geo_fence`. `customer_visit`, `loan_application`, and `insurance_application` are selectable/storable on a `GeoFence` but have no real single employee-initiated action anywhere in this codebase to attach enforcement to — see decision 111. A `GeoFence` configured only for one of these three unenforced activities has no runtime effect whatsoever.
- **Overnight/multi-day continuous exceptions aren't supported**, same limitation as Module 3's own Temporary Access — `GeoException`'s date+time window is a *daily recurring* band (decision 022), not one continuous span, and can't cross midnight (`within_daily_window`'s `"HH:MM"` string comparison).
- **Fence overlap is a warning, not a hard block.** Two active fences whose radii overlap are both allowed to exist and both remain enforceable — flagged to the Owner in the create/edit response (`overlaps_with`) but never rejected. If this should instead be a hard conflict, that's a business-rule decision the spec didn't make explicit, not an oversight.
- ~~**No hard delete of a Geo Fence with a revoked/expired (non-active) `GeoException` still referencing it.**~~ Moot as of decision 123 — `GeoException` no longer references any specific `GeoFence` at all (it bypasses whichever fence(s) would otherwise apply), so deleting a `GeoFence` is never blocked or affected by any `GeoException`, active or not.
- **No live GPS/browser testing was possible in this environment** — `enforce_geo_fence` is fully unit- and integration-tested (30 tests in `tests/api/test_geo_fencing.py`, covering every branch including the haversine distance math with real coordinates), but no actual mobile browser's `navigator.geolocation` was exercised end-to-end; `frontend/src/shared/geolocation.ts`'s permission-denied/timeout/unavailable handling was verified by code review only, same "no automated browser testing" caveat every prior module has recorded.
- **`Verify Documents`'s geo-check is unit-tested via the shared `enforce_geo_fence` engine directly (with `GeoActivity.DOCUMENT_COLLECTION`), not through a full Loan/Insurance case lifecycle end-to-end test.** `create_lead` (a much lighter fixture chain) is the one activity proven end-to-end through the real HTTP endpoint; Loan/Insurance's wiring is identical code (same function, same optional-body pattern) and was verified by code review + the shared engine's own exhaustive unit tests rather than duplicating `test_workflow.py`'s heavy case-setup fixtures for a redundant check.
- ~~**Stages 2 (MSG91 + Communication Providers) and 3 (Bulk Messaging + CRM record linkage) are not started.**~~ Stage 2 is done — see the dedicated section below. **Stage 3 (Bulk Messaging + CRM record linkage) remains not started** — ad-hoc "Send message from a Lead/Customer record" and bulk sending are separate, later work.

### Stage 2 — MSG91 + Communication Providers

- **Only the MSG91 SMS delivery-report webhook payload shape is confirmed against official documentation.** The `POST /communication/webhooks/msg91` endpoint parses `requestId`/`status`/`telNum`/`deliveryTime` (SMS DLR, sourced from docs.msg91.com/msg91.com's own webhook help pages). A real WhatsApp delivery-report callback's field names were not independently confirmable in this environment and are not parsed — such a callback is safely treated as a malformed/unrecognized payload (ignored, not mis-parsed as an SMS one) rather than guessed at.
- **The MSG91 balance-check endpoint's exact response contract (used for Test Connection) was not confirmed against a live account.** `_test_msg91_authkey` classifies success/failure by HTTP status code only (200 = pass, 401/403 = auth failure, other 4xx/5xx = failure) — the same conservative posture the pre-existing generic WhatsApp/SMS testers already use for an unconfirmed contract.
- **MSG91 Email has no MSG91-specific code at all, by design.** It sends via the exact same, already-real generic SMTP adapter every other SMTP-based email provider uses — MSG91 issues standard SMTP relay credentials (host/port/username/password) rather than a custom API contract, so there was nothing MSG91-specific to build or guess.
- **WhatsApp template variables are positional, mapped from this CRM's own `{{variable}}` declaration order** (`CommunicationTemplate.variables`) onto MSG91's `body_1`/`body_2`/... slots. If a template author reorders/renames variables after MSG91's own dashboard-side template was already approved with a different variable order, the two can silently drift — there is no cross-validation against MSG91's own approved template definition (this CRM has no read access to MSG91's template catalog).
- **The DLR webhook's shared-secret verification is a secret embedded in the callback URL (`?secret=...`), not a cryptographic signature.** MSG91 does not publicly document an HMAC/signature-based webhook authentication scheme (unlike, e.g., Meta's `X-Hub-Signature-256`) — a secret-in-URL is the standard, honest fallback for a provider without one, but is weaker than a signed payload if the URL itself ever leaks (e.g. via server access logs). Rotating the secret (edit the MSG91 config, then update the URL in MSG91's dashboard) is a fully manual process — no rotation UI/automation exists.
- **No live MSG91 account/credentials exist in this environment.** Every adapter, tester, and webhook code path is real, working code — exercised only via mocked/monkeypatched provider responses in `tests/api/test_msg91.py`, never against MSG91's actual servers. Do not treat this as production-verified until tested against a real MSG91 account with real credentials.
- **No automated browser testing**, same caveat as every prior module — verification was `tsc`/`eslint`/`vite build`/static checks plus the backend's mongomock/fakeredis test suite; the Communication Providers page's actual UI click-through (Add → fill MSG91 fields → Test → Save → Enable/Activate) was verified by code review and the underlying API's own test coverage, not an actual browser session.

### Stage 3 — Bulk Messaging + CRM Record Linkage

- **Bulk Messaging recipient selection reuses the existing Lead/Customer staff search (`GET /leads`/`GET /customers`) rather than a dedicated filter engine.** The original spec's mockup named Product/Status/Location/Date/Assigned-Employee filters; this round deliberately scoped down to "search + multi-select" (backed by each list endpoint's own existing `search` query param) to avoid building a second, parallel filter-query system or touching the Lead/Customer list pages/backends at all. An Owner can still reach any subset reachable via those endpoints' own search, just not via a dedicated multi-filter form.
- **Bulk Messaging variables are limited to `customer_name`/`mobile`/`email`**, resolved directly from the Lead/Customer record at enqueue time. The original spec's example (`{{application_code}}`, `{{loan_amount}}`, `{{status}}`, `{{secure_link}}`) would need a per-recipient join into Loan/Insurance cases (and, for `secure_link`, generating one per recipient) — out of scope for this round; a template referencing an unsupported variable simply renders the literal `{{placeholder}}` unchanged (the template engine's own existing, pre-Stage-3 behavior — never raises).
- **Bulk Messaging authorization is feature-level (`communication:bulk:create`), not per-recipient IDOR-scoped**, unlike individual Send Message. A employee granted this permission can bulk-message any Lead/Customer the search endpoints return, not just ones assigned to them — a deliberate, documented choice (a "Filtered/Selected Leads" campaign is inherently cross-assignment), not an oversight. Worth explicit confirmation if a narrower rule is actually wanted.
- **`BulkMessageJob` has no job-level "failed" status.** A job always reaches `completed` once every recipient has been enqueued-or-skipped; per-recipient send failures live entirely on the individual `CommunicationQueueItem`s (visible via "View Failed"), matching how every other queued message's failure is tracked — there is no "3 recipients failed to even enqueue" job-level flag distinct from `skipped_count`.
- **No cross-tab live progress updates.** The Bulk Messages job list/detail panel is a point-in-time read (`GET /communication/bulk-messages/{id}`); an in-progress job's sent/delivered/failed counts only update on a manual reload, not via polling or a websocket.
- **`_resolve_lead_for_message`/`_resolve_customer_for_message` (inside `CommunicationService`) independently re-implement Lead's/Customer's own existing IDOR rules** (`LeadService.get_lead_scoped`/`CustomerService.get_customer_for_staff`) rather than importing those methods — `customer.service` already imports `CommunicationService` (the Secure Application Link flow), so importing back would be a circular import. Must be kept in sync manually if either frozen module's own assignment rule ever changes; not enforced by any shared code path or test that would catch drift automatically.
- **No live AWS/MSG91 send was possible.** All 32 new Stage 3 tests (`tests/api/test_communication_stage3.py`) run against the mongomock-backed suite with a monkeypatched provider adapter — real message delivery (WhatsApp/SMS/Email via MSG91, or any other configured provider) was never exercised against a live account in this environment, same posture as every other communication-sending code path in this codebase.
- **No automated browser testing**, same caveat as every prior module — the Send Message modal, Messages panel, and Bulk Messages composer/detail-panel UI flows were verified by `tsc`/`eslint`/`vite build` and the backend API's own test coverage, not an actual browser click-through.

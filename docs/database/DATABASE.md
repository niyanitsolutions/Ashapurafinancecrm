# Database

## Base Document Fields

Every collection (via `backend/app/shared/base_document.py`) carries:

```
_id            — Mongo ObjectId, the real primary key / reference target
status         — string, values are collection-specific and DB-driven (never hardcoded)
created_at     — datetime, UTC
updated_at     — datetime, UTC
created_by     — user id string, nullable (system-created docs)
updated_by     — user id string, nullable
is_deleted     — bool, soft delete flag
deleted_at     — datetime, nullable
deleted_by     — user id string, nullable
version        — int, incremented on every update
```

`tenant_id` is intentionally not present yet — see decision 001 in `docs/decisions/DECISIONS.md`.

In application code, `_id` is exposed as `BaseDocument.id: str | None` (populated automatically from Mongo's `_id` on any document read back from the DB — `None` only for an instance that hasn't been inserted yet). Use `.require_id()` when you know the document came from the DB and want a plain `str` without the `| None`. See decision 010.

## Embedding vs. Referencing

**Embed** only for data that is tightly bound to its parent, doesn't grow unboundedly, and is always read together with it:
- Addresses (a customer's address block)
- Small nested metadata (e.g. a document's `{filename, mime_type, size}` alongside its S3 key)

**Reference** (store the related document's `_id`, query separately) for anything that grows independently of its parent or is queried on its own:
- Leads, Activities, Notifications, Audit Logs, Tasks, Employees, Customers, Documents

Rule of thumb: if a list on the parent document could grow past a few dozen items over the entity's lifetime, it must be a separate referenced collection, not an embedded array. This is a hard rule, not a guideline — see the original requirement: "Never design collections that will grow into huge embedded arrays."

## Human-Readable IDs

Staff-facing IDs (`AFS-EMP-000001`, `AFS-CUS-000001`, `AFS-LEAD-000001`, `AFS-APP-000001`, `AFS-REF-000001`) are generated by `backend/app/utils/id_generator.py`, backed by an atomic `counters` collection (one doc per prefix). These are stored as a separate field (e.g. `employee_code`) on the owning document — `_id` remains the actual primary key and the only thing other documents reference, so this scheme can be reformatted later without touching relationships.

## BSON Has No Date-Only Type

Discovered building Module 2 (Employee's `date_of_birth`/`joining_date`): BSON only has a `datetime` type, not a bare `date`. A Pydantic model field typed `date` fails at insert with `bson.errors.InvalidDocument`, not at validation time — the error only surfaces when you actually try to write it. **Any model field representing a calendar date must be typed `datetime` (store at midnight UTC), never `date`.** The API layer (`schemas.py`) can still accept/return plain `date` in request/response shapes if you want date-only JSON — convert at the service boundary (see `backend/app/features/employee/service.py:_date_to_datetime_required` for the pattern) rather than storing `date` on the persisted model.

## Mongo Round-Trips a Datetime as Naive, Even Though Every Write Uses `utc_now()` (tz-aware)

Discovered building Module 6D's scheduler jobs (decision 072): this project's Motor client has no `tz_aware=True` configured, so a `datetime` field read back from Mongo comes back naive (no `tzinfo`) even though it was written via `utc_now()` (`datetime.now(UTC)`, tz-aware). Comparing a fresh `utc_now()` against a value just read from the database raises `TypeError: can't compare offset-naive and offset-aware datetimes`. **Before comparing a DB-read datetime against `utc_now()`, normalize it with `app.utils.datetime.ensure_utc()`** (adds `tzinfo=UTC` if missing — safe, since nothing in this project ever writes a non-UTC datetime). Comparing only `.date()` on both sides (as Access Control's lazy time-window expiry already did, decision 022) sidesteps the issue but loses time-of-day precision — use `ensure_utc` instead whenever full datetime precision matters.

## Singleton Collections

Introduced by Module 4's `company_settings` (decision 030): a collection meant to hold exactly one document is still an ordinary `BaseDocument` subclass with a unique marker field (e.g. `singleton_key: str = "default"`, unique index) rather than a hardcoded ObjectId — every repository method (`find_by_id`/`update`) keeps working unmodified. The repository exposes a `get_or_create()` that returns the existing row or inserts a sensible default on first read, so callers never have to special-case "does the singleton exist yet."

## Reverse Pointers Instead of Modifying a Frozen Collection

Introduced by Module 6B's `Customer.converted_from_lead_id` (decision 048): when a new module needs to record a relationship *back* onto an already-frozen collection (here: "this Lead has been converted"), add the pointer field to the *new* module's own model instead of touching the frozen one's schema. Querying "is X already related to a Y" becomes a query against the new collection (e.g. `customers.find_one({"converted_from_lead_id": lead_id})`) rather than a field lookup on the old one. The frozen collection's own list/detail views won't visually reflect the relationship unless that page is also updated — an accepted, documented limitation (see `docs/KNOWN_LIMITATIONS.md`) rather than a reason to reopen the freeze.

## One Collection, Discriminated, for Structurally-Similar Case Types

Introduced by Module 6C's `application_workflows` (decision 054): when two entities share a generic engine (status, assignment, timeline) but differ only in a handful of type-specific fields, prefer one collection with a discriminator field (`case_type`) and an optional, strongly-typed sub-document per type (`loan_details`/`insurance_details`) over splitting into separate collections. The generic engine code (`workflow_engine/engine.py`) operates on the shared shape only; each product module owns just its own sub-document type and the actions specific to it. A genuinely different future case type is a new discriminator value + a new optional sub-document field, not a new collection.

## Multi-Document Transactions

Mongo runs as a single-node replica set (`docker/mongodb/`) specifically so `backend/app/config/database.py:start_transaction` works — required for any flow that writes to more than one collection atomically (e.g. lead status change + audit log + notification).

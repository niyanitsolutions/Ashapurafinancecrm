# Changelog

## Unreleased

### Added — Module 9B: Lead Capture
- A single shared pipeline (`Webhook → Provider → Parser → Lead`, decision 097) that Website form, Meta Lead Ads, and the retry queue all funnel through — every successful capture calls Module 6A's frozen, unmodified `LeadService.create_lead` directly (the same reuse pattern Module 7 established), getting duplicate-flagging/id-generation/audit-logging for free.
- **Website Lead Capture** (`POST /lead-capture/website`, public, rate-limited): deliberately lenient request schema so a malformed submission still gets logged as a `CaptureFailure` (missing_required_fields/invalid_data) rather than a bare, unrecorded HTTP 422 — "never lose inbound requests."
- **Meta Lead Ads**: a real webhook — `GET /lead-capture/webhooks/meta` (verification handshake against the active Meta config's `webhook_verify_token`, Module 9A) and `POST /lead-capture/webhooks/meta` (HMAC-SHA256 signature verification via `hmac.compare_digest`, then a real, live Graph API call to retrieve each lead's actual field data — decision 100, the first place 9A's stored webhook credentials are actually used).
- **Manual API** (`POST /lead-capture/manual`, authenticated, permission-gated) — a controlled, staff-triggered capture through the same pipeline, strict validation (no `CaptureFailure` needed — an authenticated caller can just fix and resubmit).
- **System actor for unauthenticated captures** (decision 098): a real, persisted Owner satisfies `create_lead`'s actor requirement, then `created_by` is nulled out immediately after — the same precedent Module 6B's direct-portal registration already established. The real provenance (source, external id) lives on the Lead's own Timeline via a new `LeadActivity(event_type="captured")` row instead.
- **Capture Failures + Retry Queue** (decision 099): every non-`api_error` failure (duplicate/invalid_data/missing_required_fields) is permanent, logged for visibility; `api_error` (transient/technical) retries automatically via a new Arq cron job (`retry_capture_failures`, every 15 min) with exponential backoff, giving up as `exhausted` after 5 attempts. A manual "Retry Now" is also available.
- **Idempotency** (decision 101): `CaptureReceipt` prevents a retried Meta webhook delivery for the same `leadgen_id` from creating a duplicate Lead — Website/Manual rely on 6A's own existing cross-lead `duplicate_of_lead_ids` flagging instead, unaffected by this check.
- **Source Mapping** (decision 102): a seeded `CaptureSource` catalog (website_form/meta_lead_ads/manual_api → a Module 4 Lead Source, plus an optional default product mapping for Meta) — Owner-remappable via `PATCH /lead-capture/sources/{key}`, never hardcoded.
- ~8 endpoints (2 public — website form, Meta webhook GET+POST; 6 staff — manual capture, sources view/edit, failures view + manual retry), gated by `require_permission("lead_capture", "captures"|"sources"|"failures", action)`. Frontend: one combined `LeadCapturePage` (Source Mapping, Manual Capture form, Capture Failures list with Retry Now).
- `tests/api/test_lead_capture.py` — 10 new tests (144 total across the suite): Website capture success + Lead Source mapping, missing/invalid-data failures, Manual capture permission gating, Meta webhook verification handshake, invalid-signature rejection, successful capture + idempotent redelivery (Graph API call monkeypatched), transient-failure queuing, retry-queue resolve + exhaust, Source Mapping admin endpoints, Capture Failures list + manual retry.
- Per a follow-up review before freeze (decision 103): a reserved (inert) `webhook_events` collection for future observability, plus a Lead Source Metadata / Website Form Version passthrough (`form_id`/`form_version`/`campaign_id`/`adset_id`/`ad_id`/`utm_source`/`utm_campaign`/`utm_medium`) recorded on the Lead's own Timeline whenever a source's payload actually supplies one — never fabricated when absent.

### Added — Module 9A: API Management
- Scoped explicitly to the integration *management* platform only, per explicit instruction — no WhatsApp message, Meta lead, SMS, or email is ever sent from this module; Test Connection is the only external call, and never a business action.
- New, additive `features/integrations` module (not an extension of frozen `system_settings.ApiSetting`, which already stores encrypted provider config but lacks the concepts this module needs — decision 091). Three new collections: `integration_providers` (seeded catalog), `integration_configs`, `integration_test_logs`.
- **Multiple named configurations per integration type, one Active** (decision 092) — the user's own recommendation, given before implementation: an Owner can create "Meta Production"/"Meta Sandbox"/etc., each independently credentialed; activating one auto-deactivates any other active config of the same type. `is_enabled` (ready) and `is_active` (currently live) are separate flags.
- Config storage reuses Foundation's `security/encryption.py` unmodified (the same primitive as `ApiSetting`, decision 028) — one encrypted blob per config, updates merge rather than replace. Secret fields (App Secret, Access Token, Webhook Verify Token, Webhook Secret, API Key, Password) are masked to their last 4 characters in every API response — detected by naming convention, never returned in full (decision 093).
- Test Connection (decision 094): real, live checks for Meta (Graph API `/me`) and Google Maps (Geocode API) — well-known single APIs; generic HTTP reachability checks for WhatsApp/SMS/API-based Email (open-ended, multi-provider by design); a real SMTP connection + STARTTLS + login handshake (standard library, no message sent) for SMTP Email. Every attempt records `{success, response_time_ms, error_message}` to both the config's own `last_*` fields and an append-only test-log history.
- "Integration Type → Provider → Configuration → Status," never hardcoded (decision 095) — a seeded `integration_providers` catalog (6 rows: meta/meta, whatsapp/whatsapp_business_api, sms/generic_sms, email/smtp, email/email_api, maps/google_maps); adding a future provider is a new seeded row, not a code change.
- ~11 endpoints (providers list, configs CRUD+enable/disable/activate/test/test-logs), gated by `require_permission("integrations", "configs", action)` — real, Owner-delegable Access Control, reused not duplicated. Frontend: `IntegrationListPage` (grouped by type, Add Configuration form driven by the provider catalog), `IntegrationDetailsPage` (status, Enable/Disable, Set Active, Test Connection, edit form, test history) — exactly the 5 frontend pieces scoped (no webhook setup screens).
- `tests/api/test_integrations.py` — 7 new tests (134 total across the suite): permission gating + provider catalog, encryption/masking round-trip (asserting the stored blob is genuinely ciphertext, not plaintext JSON), unknown-provider rejection, update-merges-without-exposing-old-secrets, the full enable/disable/activate lifecycle (including "only one active per type" and "disabling clears active"), Test Connection success/failure recording (network calls monkeypatched — no live credentials exist anywhere in this project), and integration-type filtering.
- Per a follow-up review before freeze: `IntegrationConfig` gained a reserved (not implemented) `health_status` field (decision 096) — "no need to implement now, just reserve it for later." `integration_test_logs` was confirmed permanent, unbounded history by design (no TTL/pruning/delete) — already how it was built, not a change.

Per explicit instruction, this is **not** fixed by modifying frozen Module 6C now — recorded as a deferred Phase 2 schema improvement (`submitted_at`/`approved_at`/`rejected_at`/`disbursed_at`/`policy_issued_at`), to be implemented only if reporting accuracy requirements demand it later (decision 089).

### Changed — Module 6D: two small enhancements (post-approval review, before freezing)
- **Notification Category taxonomy** (decision 073): every `Notification` now carries a `category` — `assignment`/`reminder`/`task`/`workflow`/`document`/`system`/`security` — derived automatically from its `notification_type` (never caller-supplied), so classification can't drift from the type that produced it. `GET /notifications?category=` added; `workflow`/`system`/`security` are reserved for future notification types with no producer yet. `NotificationListPage` gained a category filter dropdown and a badge on each card.
- **Reminder Rules now support multiple independent trigger points** (decision 074): `notify_before_days`/`notify_before_minutes` changed from a single value to `list[int]` (e.g. `[30, 15, 7, 1]`), per the user's own worked example. Each configured offset fires and is tracked independently (`Reminder.trigger_offset`) — a case or task that has crossed several thresholds since the last scheduler run catches up on all of them in one pass. Seeded rules still configure a single offset each; this is added capacity, not a change to current behavior. `ReminderRulesPage` takes a comma-separated list for these fields.
- `tests/api/test_reminders.py` — one new test (`test_check_re_eligible_cases_fires_each_configured_trigger_point_independently`) plus category-filter assertions added to the existing inbox test; **113 tests total** across the suite.

### Changed — Module 6C: business refinement (post-approval review, before freezing)
- **Insurance lifecycle finalized.** The user reviewed the draft flagged as an assumption (decision 057) and replaced it with a corrected, final sequence (decision 064): Application Submitted → Documents Pending → Underwriting → **Medical Verification** (optional) → **Additional Documents** (optional) → Premium Acceptance → **Policy Generation** → **Policy Issued**. Both optional stages are per-case flags recorded once during Underwriting (`requires_medical`, `requires_additional_documents`); Policy Generation (policy number recorded, `POST /insurance-cases/{id}/policy/generate`) and Policy Issued (terminal, `POST /insurance-cases/{id}/policy/issue`) are two distinct actions, not one. The former `active` terminal status is removed.
- **"On Hold" / "Resume" added to both pipelines**, per the user's explicit recommendation and instruction ("Don't hardcode it. Make it Workflow Definition → Optional Status"). Every non-terminal status on both pipelines gains `on_hold` in its own `allowed_next_statuses` (seeded config); a closed `HoldReason` vocabulary (waiting for customer/bank/insurance company, internal review, document clarification) is required. Implemented as two calls into the existing generic `WorkflowEngine.transition()` (`backend/app/features/workflow_engine/hold.py`) — `put_on_hold` records the case's current status before moving it to `on_hold`; `resume` reads that status back out and transitions there. No new engine validation logic. New endpoints: `POST /{loan,insurance}-cases/{id}/hold`, `POST .../resume`.
- New `ApplicationWorkflow` fields: `on_hold_reason`, `on_hold_previous_status`, `on_hold_since`. `InsuranceCaseDetails` gains `requires_additional_documents`, renames `medical_outcome`/`medical_remarks` → `medical_verification_outcome`/`medical_verification_remarks`, and splits `policy_issued_at` into `policy_generated_at` + `policy_issued_at`.
- Frontend: both Case Details pages gain a "Case Status Control" panel (Hold form with a reason dropdown, or a Resume button while on hold); Insurance's Underwriting decision screen gains a second checkbox ("Requires additional documents"); Policy Generation/Policy Issued are now two separate steps in the UI.
- `tests/api/test_workflow.py` — updated the two Insurance pipeline tests for the finalized statuses/endpoints, added `test_insurance_pipeline_with_medical_and_additional_docs`, `test_insurance_medical_verification_failure_rejects_case`, and `test_loan_case_hold_and_resume` (5 new/changed tests total; 105 tests across the suite, up from 103).

### Fixed — Foundation
- `BaseDocument` was missing a usable `id` field — Pydantic v2 silently dropped Mongo's `_id` on every read. Added `id: PyObjectId | None` aliased to `_id`, plus a `require_id()` helper; `BaseRepository`'s `TModel` bound tightened to `BaseDocument` accordingly. See decision 010.
- `backend/app/middleware/rate_limit.py` called the Redis singleton directly instead of through FastAPI dependency injection, bypassing `dependency_overrides` (found because it broke test isolation) and making the Redis client unswappable in general. Now takes `redis: Annotated[Redis, Depends(get_redis)]`.
- Replaced `passlib[bcrypt]` with direct `bcrypt` calls — passlib's backend detection is broken against `bcrypt>=4.1` and the library is unmaintained.
- `security/jwt.py` `TokenType` gained a third value (`OTP_VERIFIED`) and `_expiry_for` is now a lookup rather than an if/else, so adding further token types doesn't require touching `_create_token`'s branching again.
- Mongo/Redis clients had no connection timeout — a down/unreachable service would hang requests indefinitely instead of failing fast. Added `serverSelectionTimeoutMS`/`socket_connect_timeout` (5s each).

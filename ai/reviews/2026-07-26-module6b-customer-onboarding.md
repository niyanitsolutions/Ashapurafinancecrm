# 2026-07-26 — Module 6B: Customer Onboarding & Application Flow

Preceded by the user reconfirming the blanket freeze across all seven completed modules (Foundation through Lead Foundation, Module 6A) before handing over 6B, and by an unprompted refinement to the brief's own conversion-timing sentence — swapping a single ambiguous line for one that explicitly distinguishes the two onboarding flows' Customer-creation timing. That refinement was adopted verbatim and became the anchor for the module's central design decision (047).

The single hardest problem this module posed: the brief said "Authentication must reuse Module 1. Do not modify Authentication," but Module 1's whole signup design (decision 011) requires an already-authenticated Owner/Employee to invite anyone before an OTP can be issued — and Flow 2 (a customer walking up to the public portal cold, with no prior staff contact) structurally has no such inviter. Reconciling "reuse, don't modify" with "there's no human inviter" took real thought: `AuthService.send_otp`'s signature takes `inviter: User` as a plain parameter, not something hardcoded to the HTTP caller — so Module 6B's own service supplies a *resolved* User for each flow instead. Flow 1 uses the actual Employee/Owner who generated the secure link (a real, legitimate inviter, just resolved asynchronously once the customer clicks through later). Flow 2 uses any seeded Owner account as a technical stand-in — reasoned as "the business itself operates the public portal and implicitly authorizes anyone who applies through it." This was flagged explicitly (decision 049) as the one place in the whole reuse strategy that required judgment rather than a mechanical read of the brief, rather than being quietly buried in a code comment.

The second major design fork was where Personal/Contact/Address/KYC information lives, given the brief demanded both "the form structure must be dynamic... do not hardcode forms" *and* a distinct, separately-described "Customer Profile" concept. Reading the two flow diagrams literally resolved it: Flow 2 creates the Customer (and asks for profile info) *before* any product is chosen; Flow 1 goes straight from login to "Application opens directly," with no separate profile screen shown at all — and per the user's own refined wording, no Customer row exists for Flow 1 until submission. The synthesis: personal/KYC fields are a *fixed* schema, never part of the dynamic `ApplicationFormDefinition`, collected via a dedicated screen for Flow 2 and inline within the application itself (a `pending_profile` field, consumed and cleared at submission) for Flow 1. The dynamic engine stays purely about product-specific fields — which is also the cleaner reading of "do not hardcode forms," since personal/KYC fields don't vary by product the way loan amount or sum insured do.

Recording the Lead→Customer conversion without touching Module 6A required the same discipline as every prior module's frozen-boundary problem: rather than adding a status value or a new field to `Lead`, the pointer lives on the *new* module's own model (`Customer.converted_from_lead_id`). Checking "has this lead converted" becomes a query against `customers`, not a Lead field — and it's also what blocks generating a second secure link for an already-converted lead. The cost is that Module 6A's own Lead List/Details pages show no visual "converted" badge; accepted and documented rather than edited around.

A related, quieter judgment call: whether Employee visibility into Customers/Applications should go through Access Control's `require_permission`, the pattern every module since Settings has used. The brief's own capability lists settled it — Employee access is described as inherent ("View Assigned Customers/Applications"), and Owner-only actions (assigning) are named exclusively under Owner's list, with no hint of Owner delegating that capability to specific Employees. Since an Employee's view is hard-scoped to their own assignments in the service layer *regardless* of any permission grant, adding `require_permission` here would have been ceremony without real flexibility — the same reasoning Module 2 used to justify never adopting `PermissionEngine` in the first place. This is 6B's one deliberate departure from the pattern every module since Access Control has followed, recorded prominently (decision 050) rather than silently deviating.

The dynamic form engine itself needed one seeded-content decision: an empty catalog (Module 4's approach for Status Masters/Notification Templates) would have left the module's central deliverable — "the engine actually renders and validates a real form" — unverifiable end-to-end. Five plausible, generic field lists were seeded instead, explicitly labeled as illustrative rather than authoritative, alongside a new "Property Documents" document type (added through Module 4's own still-open create endpoint, not a code change).

A smaller, discovered-along-the-way gap: "Generate Secure Link" naturally belongs on Module 6A's Lead Details page, but that page is frozen — adding a button there would be a new capability, not a bug fix. Built as a standalone, URL-reachable page instead, with the gap documented rather than papered over — the same honesty pattern already established for Module 4's undiscovered CSV-export bug and Module 6A's own Create-Lead-dropdown permission gap.

# 2026-07-25 — Module 6A: Lead Foundation

Preceded by the user reissuing the blanket freeze, this time explicitly naming all six completed modules including Dashboard Framework, before handing over Module 6 — "the heart of the CRM," explicitly flagged as likely the largest module in the system. The user's own recommendation, given unprompted, was to split it into four sub-modules (6A Lead Foundation, 6B Customer Application Flow, 6C Loan & Insurance Pipeline, 6D Re-Eligible & Reminder Engine) and build them one at a time rather than accepting a single giant prompt — a self-aware scoping move that made this pass tractable. This review covers 6A only.

The central design question was what a "Lead" actually *is* at this stage, given the brief's own bullet list splits "Lead entity/CRUD/Duplicate Detection" (6A) from "Customer Creation/Secure Link/Portal connection" (6B). Since `Customer` is still an empty scaffolded module, a Lead can't reference one yet — so it carries raw contact info (`full_name`/`mobile`/`email`) directly on itself. This isn't a shortcut; it's the correct shape for what duplicate detection actually needs (comparing against existing prospects *before* any conversion happens), and it cleanly separates "did we already hear from this person" (6A) from "do they have portal access and a submitted application" (6B, later).

Duplicate Detection itself needed a real behavioral call the brief didn't specify: block or flag? Blocking outright risks silently dropping a legitimate second inquiry with no trace it happened — a materially worse failure mode for inbound lead capture than a false-positive flag a human can dismiss. Chosen: always create, always flag (`duplicate_of_lead_ids`, every prior match), plus a standalone pre-submission check endpoint for the UI to warn with before the user even hits submit. Matching is on `mobile` alone, not product-scoped or time-windowed — flagged explicitly as an assumption, not a confirmed rule, since a real duplicate-detection policy is exactly the kind of business logic that shouldn't be guessed at more precisely than the brief supports.

"Timeline," "Notes," and "Activities" were three separate bullets in 6A's own scope, distinct from the project's already-reserved, still-empty `features/timeline` module (meant for a future cross-entity version). Built a small, lead-scoped pair instead — `LeadActivity` (system-logged) and `LeadNote` (user-authored), merged and sorted in one `GET /leads/{id}/timeline` response — matching the project's established pattern of shipping a narrow, real version before a generic one exists (the same shape as Module 2's `employee_documents` predating any generic Document Management). Every mutating action also mirrors into the shared `audit_logs` collection, keeping the Recent Activities dashboard widget (Module 5) meaningful for Lead events too, not just a second, disconnected activity log.

The most consequential validation of prior architecture happened almost by accident: Dashboard Framework (Module 5) had deliberately left `today_leads` and `assigned_leads` as honest placeholders, referencing `module="leads", resource="leads"` permissions that didn't exist yet, on the explicit bet that a future module could wire them up for free. Module 6A did exactly that — added the `leads:leads` permission-catalog entry (the same name Dashboard's seed data already used) and two new provider functions, and the widgets started computing real counts with zero changes to Dashboard's engine, router, or catalog. Verified end-to-end (not just unit-tested) in `test_dashboard_today_leads_and_assigned_leads_widgets_reflect_real_data`, which exercises the full stack: create a Lead via the real API, assign it, then read the number back through `GET /dashboard`. `pending_followups` stayed a placeholder — it needs a reminder/follow-up date that plainly doesn't exist until Module 6D, and wiring it up now would mean fabricating a "follow-up" concept out of nothing.

One real usability tension surfaced and was deliberately left unresolved rather than patched around: Create/Edit Lead's Source and Product dropdowns call Module 4's own Settings endpoints, each gated by its own `system_settings:*` permission — separate from `leads:leads`. An Owner granting only the Leads permission to a role will find that role's Create Lead form has empty dropdowns. Bundling Settings' read access into the Leads permission, or adding a backend proxy, would both be new precedent-setting exceptions to "every permission is scoped to exactly one resource" (decision 021) for the convenience of one form. Left as a documented consequence of the existing design instead — a good example of a rough edge that's honestly a rough edge, not something the model should paper over.

A pre-existing bug in a frozen module surfaced along the way, unrelated to this pass but worth recording: Module 2's Employee List "Export CSV" button is a plain `<a href>` to a protected endpoint — since this app is pure-Bearer with no cookies, a bare anchor navigation can never carry the Authorization header, so that button has likely never actually worked. Module 6A's own Lead export was built correctly from the start (authenticated `fetch` → blob → triggered download, via a new `getAccessToken()` export added to the shared API client), but Module 2's file was left untouched rather than opportunistically fixed — flagged in `docs/KNOWN_LIMITATIONS.md` as a real bug-fix candidate under the freeze policy's own bug/security exception, for the user to decide whether to greenlight.

Verification: `ruff`/`mypy` clean (143 backend files), 88/88 tests passing (13 new, including a stale Module 5 test caught and fixed — `today_leads` was no longer a valid example of "not yet available" once this module wired it up), frontend `tsc`/`eslint`/`build` clean (173 modules, though the bundle has now crossed Vite's 500kB size-warning threshold — noted, not addressed, since code-splitting is a bigger call than this module needs to make).

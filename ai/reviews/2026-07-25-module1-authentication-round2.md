# 2026-07-25 — Module 1: Authentication, round 2 (post-review hardening)

The user reviewed the initial Authentication build and declined to freeze it, raising five concrete concerns before approval: refresh-token storage trade-offs weren't documented, Customer/Referral Partner signup was open rather than matching the actual staff-initiated business workflow, Owner signup needed to be explicitly documented as seed-only, Login History needed more fields, and refresh token rotation should detect reuse (family invalidation).

One genuine scope tension surfaced again: closing "open signup" per the business workflow diagram (Website Lead → Employee → Generate Secure Link → Customer signup) still can't produce a real clickable link, because the link's target — a Lead — doesn't exist until Lead Management is built (already flagged as deferred in round 1). Resolved by implementing the security-relevant core — no public signup entry point, staff-authorized invitation — through the existing `send-otp` endpoint (now requiring Owner/Employee auth + a role-authorization check) rather than adding a 10th API or fabricating a fake link. This was stated explicitly rather than silently narrowing scope; see decision 011.

Refresh token storage was the one item phrased as "don't change it blindly, document the reasoning" rather than a direct instruction — treated as asking for a thorough trade-off writeup and a confirmed choice, not a fresh blocking question, since the user had just re-confirmed the "no cookies" architecture in round 1 and this was already a natural extension of that. `localStorage` was kept (the alternatives — sessionStorage, IndexedDB — are the same XSS-exposure class, and memory-only would force re-login every reload with no Dashboard yet to soften that), with the reuse-detection feature (decision 013) doing the real risk-bounding work: a stolen refresh token is now usable at most once before its whole family is killed. Full reasoning in decision 012.

Refresh token family/reuse detection required a real mechanics change: rotation no longer updates a session document in place, it retires it (`status: rotated`) and inserts a new chained row. This let a genuine edge case in round 1's test suite surface — a test asserting "reuse of an old refresh token fails" would now, as a side effect, revoke the entire family including the token the test needed for a later step. Tests were restructured accordingly rather than papered over.

Verification: 20/20 tests passing (5 new: invitation authorization enforcement both directions, `send-otp` auth requirement, failure-reason audit detail, full Login History field coverage, reuse-detection family revocation). `ruff`/`mypy --strict` clean. Frontend `tsc`/`eslint`/`build` clean after removing the now-invalid self-signup UI.

Per the user's explicit instruction, this is now stated as frozen: no further architectural changes to Authentication without explicit approval; future modules consume its APIs.

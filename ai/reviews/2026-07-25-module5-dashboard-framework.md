# 2026-07-25 — Module 5: Dashboard Framework

Preceded by a blanket freeze: the user formally froze all five completed modules (Foundation, Authentication, User & Employee Management, Access Control, Settings) under one rule — "No architectural modifications. Only Bug Fixes or Security Fixes" — the first time Foundation itself was ever given an explicit freeze statement rather than being referred to as frozen in passing. Recorded as decision 031 before any Module 5 code was written.

The user's brief was explicit that Dashboard is "NOT just charts" and gave three buckets: Layout (Sidebar/Topbar/Profile Menu/Notification Bell/Quick Search/Theme/Responsive), Dashboard Widgets (13 named), and a Dashboard Engine (each widget permission-based, configurable: hide/show/order/refresh interval) — with Lead/Customer CRUD and Loan/Insurance processing explicitly excluded.

The central design problem: almost every named widget (Today's Leads, Disbursed, Rejected, Revenue, Referral Summary, ...) depends on data from modules that don't exist yet (Leads, Loan/Insurance Management, Referral Partner, Reminders, Notification Management). Two options existed — invent placeholder/fake numbers, or build the full engine honestly and let most widgets say "not available yet." The second was chosen without much debate: fabricating numbers would violate the project's standing discipline against inventing unconfirmed business content (the same reasoning behind Module 4 shipping Status Masters/Notification Templates empty). Concretely: `widget_providers.py` computes genuine values for exactly 3 widgets (Recent Activities from the shared `audit_logs` collection; Department Summary and Employee Summary from Module 2's own collections, read-only) and an honest `{available: false}` for the other 10.

This turned into the module's most interesting design win: since widgets/nav items are gated by `PermissionEngine.has_permission`, and that engine already returns `False` for any (module, resource) with no catalog entry, referencing not-yet-built modules' names in a widget's `required_module` field costs nothing today and becomes instantly, correctly functional the moment that module is built and seeds its own permission catalog entry — no Dashboard code change required. Proven directly in `tests/api/test_dashboard.py` by hand-creating a `leads:leads:view` permission and confirming the `today_leads` widget becomes grantable.

A real bug was caught during design, not after: the natural instinct was to gate every Sidebar nav item by a `require_permission` check. But Module 2 (Employees) and Module 3 (Roles & Permissions) were never retrofitted to use `PermissionEngine` at all — their routes are still plain `require_owner`. Gating those nav items by permission would have let an Owner grant an Employee a permission that makes the nav item appear, only for the linked page to 403 immediately on click. Resolved by adding a second, simpler `owner_only` gate to `NavItem` that mirrors what's actually true today, alongside the `require_permission`-style gate used for Settings (which really is permission-gated). The lesson: a nav/visibility layer has to describe the *actual* authorization of what it links to, not an aspirational, more-elegant-looking one.

The other notable decision was completing two things Foundation had explicitly deferred to this exact module. `AppShell`/`Sidebar`/`Topbar` were literal Foundation-era placeholders whose own docstrings said as much ("Authentication is the next module; it will gate this shell" — never happened; `SimplePageLayout`'s docstring: "building that out is Dashboard Framework's job"). Module 5 wires the real shell around every authenticated route via `<Outlet/>`, while deliberately not touching any existing page's own `SimplePageLayout` header — accepting a minor visual redundancy (two header rows) over risking a frozen page component. Separately, `POST /auth/logout` had existed since Module 1 with zero frontend callers; Profile Menu is the natural home for a real Logout action, implemented by calling that already-tested endpoint from a brand-new Dashboard file — zero lines changed under `features/auth/`, justified under the freeze policy's "security fix" exception (an unrevoked refresh token left dangling after a user believes they've logged out).

Refresh Interval (one of the four required "configurable" behaviors) was implemented as a genuinely functional single shared poll — computing the shortest configured interval across visible widgets and refetching the one combined `/dashboard` payload on that cadence — rather than either leaving it a stored-but-inert number (the trap Module 4's Company Settings theme fields fell into) or building N independent per-widget polling loops that would all refetch the same payload redundantly.

Verification: `ruff`/`mypy` clean (134 backend files), 76/76 tests passing (11 new), frontend `tsc`/`eslint`/`build` clean (168 modules). No live MongoDB/Redis was available in this environment (no Docker), so — same as every prior module — verification relied on the mongomock/fakeredis-backed test suite and static frontend checks; the responsive Sidebar drawer in particular was verified by code review only, not an actual mobile-viewport browser session.

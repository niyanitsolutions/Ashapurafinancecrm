# 2026-07-25 — Module 4: Settings (Master Data)

Delivered after the user emphasized this module's importance up front ("Everything later depends on it") and gave a flat list of master-data categories: Departments/Designations/Branches, Lead Sources, Loan Products, Insurance Products, Status Masters, API Settings, Company Settings, Notification Templates, Document Types — each with a few literal examples, no further scope narrowing needed.

The central design tension was the same shape as every prior module's freeze problem, but inverted: Departments/Designations/Branches already exist as Module 2 collections with only `GET`/`POST`, and decision 019 had explicitly anticipated this module providing "full management screens." Since Module 2 is frozen, this module adds `PATCH .../{id}`, `/activate`, `/deactivate` from its *own* router, composing directly over Module 2's existing `DepartmentRepository`/`DesignationRepository`/`BranchRepository` (their inherited generic `update`, already public via `BaseRepository`). No new path collides with Module 2's `GET`/`POST`, and zero lines changed under `app/features/employee/` — the same read+write reuse pattern Module 2 itself used against Auth's `SessionRepository` in Module 2, now applied one module further down the chain.

The second major decision was purely architectural: with 8 new resource types and 3 extended ones, writing every list/create/edit/activate/deactivate handler out by hand (Module 2/3's usual style) would have meant ~10 near-identical copies of the same logic. Four of the eight new resources (Lead Sources, Loan Products, Insurance Products, Document Types) are genuinely identical in shape — `name + description + status` — so this module introduces its first shared abstraction: one `NamedMasterData` Pydantic base, one generic service-layer CRUD path, and one generic React component (`NamedMasterDataPage`), reused six times (including Department/Designation editing). This was a deliberate, scoped exception to the project's usual "write it out explicitly" convention, justified by genuine duplication across a known, immediate set of resources rather than a speculative future one — Status Masters/Notification Templates/API Settings/Company Settings all have real shape differences and got dedicated code instead.

The third decision was about what *not* to invent. The brief named Status Master *categories* (Loan/Insurance/Customer status) and Notification Template *channels* (SMS/Email/WhatsApp) but no concrete status values or message copy. Both are exactly the kind of business-logic content this project's discipline says not to invent (see `docs/REQUIREMENTS.md`'s Open Business-Logic Questions) — the collections and full CRUD UI ship, but `scripts/seed.py` seeds zero example rows for either. By contrast, Lead Sources/Loan Products/Insurance Products/Document Types *were* seeded, because the user typed literal example values for those directly in the brief — seeding them is honoring the given examples, not inventing new ones.

The fourth decision resolves a loose end from Module 3: `PermissionEngine`/`require_permission` were built and unit-tested but consumed by nothing (flagged explicitly in Module 3's `KNOWN_LIMITATIONS.md`). `docs/architecture/MODULES.md` had already stated the intent — "Settings (Master Data) onward should gate their write endpoints with `require_permission(...)`" — so this module gates *every* endpoint (reads included, a simplification over mixing two auth strategies) with it. Since Owner bypasses the engine entirely, behavior is identical to the `require_owner` pattern used everywhere else until an Owner actually delegates a Settings resource to an Employee role — which the test suite verifies end-to-end (deny → grant → allow → still-denied-for-an-ungranted-action), not just via the engine's own unit tests as Module 3 had to settle for.

API Settings needed one more judgment call: credential storage. Reusing Module 2's bank-account-number encryption primitive (`app.security.encryption`) but applied to a whole flexible JSON blob (since provider config shape varies entirely by provider) rather than a fixed schema per provider — data-driven, consistent with the rest of the project. Config is merged (not replaced) on update and never echoed back in plaintext, only the configured key *names*.

Verification: `ruff`/`mypy` clean (124 backend files), 65/65 tests passing (11 new), frontend `tsc`/`eslint`/`build` clean (161 modules). No live MongoDB/Redis was available in this environment (no Docker), so — same as every prior module — verification relied on the mongomock/fakeredis-backed test suite and static frontend checks rather than a live dev-server smoke test.

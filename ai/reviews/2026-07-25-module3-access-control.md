# 2026-07-25 — Module 3: Role, Permission & Access Control

Delivered after the user explicitly froze Module 2 (exact wording recorded in `docs/decisions/DECISIONS.md`) and scoped Module 3 tightly: Roles, Permissions, Employee↔Role assignment, Permission Matrix, Module access, Action permissions, Temporary Access, Geo-fencing Exceptions, Audit Logs — with Dashboard/Leads/Customers/Loans/Insurance/Reports/Notifications/Settings explicitly out. The user also gave a concrete design instruction: since the CRM will become a SaaS product, don't hardcode module names into the permission system — make it data-driven, with a worked example (`module: loan_management, resource: leads, actions: [...]`).

The main design tension, same shape as Module 2's: Access Control needs to resolve permissions *for* an Employee, but Module 2 is frozen. Resolved the same way — read-only reuse. `PermissionEngine` and `AccessControlService` both import Module 2's `EmployeeRepository`/`require_owner` directly; zero lines changed under `app/features/employee/`. Documented as decision 024 so the pattern is traceable rather than silently repeated.

The data-driven instruction was taken literally: `Permission.module`/`Permission.resource` are free-text strings, not enums, validated only against a fixed `PermissionAction` vocabulary (13 actions, given as a closed set in the brief — unlike module/resource, this one *is* meant to be fixed). Foundation already had a `permission_key(feature, action)` helper in `app/constants/permissions.py` from the original scaffold; it uses a different two-part key shape and was left untouched and unused (decision 021) rather than retrofitted, since Foundation is also frozen and the shapes don't reconcile cleanly.

Two genuine ambiguities were resolved by interpretation, not invention-then-silence: (1) the brief's four separate fields (Start Date/End Date/Start Time/End Time) for Temporary Access and Geo Exceptions were read as a *daily recurring* window rather than one continuous span (decision 022) — flagged in both `DECISIONS.md` and `KNOWN_LIMITATIONS.md` as an assumption, not a confirmed spec. (2) Geo-fencing's enforcement engine has never been defined (open since Foundation) — so Geo Exception was scoped to administrative record-keeping only (decision 023), not paired with invented enforcement logic.

`PermissionEngine.has_permission`/`require_permission` were built and directly unit-tested (owner bypass, department-scope enforcement, temporary-access window edges) but are not yet consumed by any real protected route — the modules that would call `require_permission(...)` (Dashboard, Leads, etc.) are exactly what's out of scope this round. This is expected, not a gap: the engine exists now so every module from here on is built against it instead of a bespoke role check.

Verification: `ruff`/`mypy` clean across 115 backend files, 54/54 tests passing (14 new), frontend `tsc`/`eslint`/`build` clean across 146 modules.
